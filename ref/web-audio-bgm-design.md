# Web Audio 直合成BGM 設計指針

新規プロジェクトでWeb Audio APIによる直合成BGMを実装する際、着手前に読むこと。

本書は特定プロジェクトの経験則である。前提が変われば再検討せよ。

## 0. 最初に踏む罠：AudioContextの起動

**AudioContextは必ずユーザー操作を起点に生成・resumeする。** ブラウザのautoplay policyにより、クリックやタップなしに生成したAudioContextは`suspended`のまま音が出ない。ページ読み込み時に初期化する設計にすると、原因不明の無音に悩むことになる。

```js
// 再生ボタンのクリックハンドラ内で初期化する
if(!audioCtx) audioCtx = new AudioContext();
if(audioCtx.state === 'suspended') audioCtx.resume();
```

`sampleRate`は指定せず環境依存に任せてよい。`latencyHint`はBGM用途なら既定（`'interactive'`）で問題ないが、演奏機能（鍵盤など）を付けるなら遅延が体感に直結するため実機で確認すること。

## 1. ノードのライフサイクル ★最重要

**このセクションが本書で最も重要である。** ここを誤ると、数分でメモリが数百MBに達し、音割れ・再生停止に至る。実際に最後まで残った不具合はすべてここが原因だった。

### 鉄則：接続したものは必ず切断する

Web Audioのノードは、**他のノードに接続されている限りGCに回収されない**。オシレーターが鳴り終わっても、その先のGainNodeが`masterGain`に繋がったままなら、接続グラフ上の参照が残り続ける。

```js
// 悪い例：Gainが永久にmasterGainへ繋がったまま残る
osc.connect(g);
g.connect(masterGain);
osc.start(t); osc.stop(t + dur);
```

**正しくは、発音終了時に自分が生成したノードをすべて切断する。**

```js
osc.connect(g);
g.connect(masterGain);
osc.start(t); osc.stop(t + dur);
osc.addEventListener('ended', ()=>{
  g.disconnect();
  filter.disconnect();  // 生成したフィルタ等もすべて
});
```

複数オシレーターを使う音色では、**代表として1つのオシレーターにだけ**`ended`を張り、そこで全ノードを切断すればよい。

### 管理配列からの除去だけでは不十分

強制停止用にノードを配列で保持している場合、`ended`で配列から除去する処理はメモリ対策として**不完全**である。配列から消えても接続グラフ上の参照は残る。**配列除去と`disconnect()`は別物であり、両方必要。**

### 症状の見分け方
- メモリ使用量が増え続け、GC後の下限値（谷）も回復しない → 接続の未解放
- 増えるが谷は一定 → GC待ち。実害は少ない
- 一定量を超えると音が濁り、GC後に回復する → GC実行時のオーディオスレッド停滞。ノード生成数を減らす必要がある

## 2. スケジューリング

### 曲の全ノートを一括予約してはいけない

ループ開始時に曲全体（数百〜千ノード）を一度にスケジュールすると、その瞬間の生成負荷でオーディオスレッドが詰まる。高スペック機では誤魔化せるが、**非力な環境では数分で音割れし停止する**。

### 先読みスケジューリング（"A Tale of Two Clocks"方式）

短い間隔で起き、直近に鳴る音だけを予約する。

```js
const LOOKAHEAD_INTERVAL_MS = 25;   // タイマー間隔
const SCHEDULE_AHEAD_SEC = 0.2;     // 何秒先まで予約するか

// 全パートのイベントを「曲頭からの絶対秒」でフラット化し時刻順にソート、
// カーソルを進めながら scheduleUntil までのノートだけ予約する
```

同時に存在するノードが数百個から数個〜十数個に減る。停止時の後始末も軽くなる。

### 実装時の注意
- **すべての経路で、必ず次のtickを予約するか明示的に曲送りするか、どちらかを行う。** 「何もせずreturnする」分岐が1つでもあると、エラーも出ないまま無音で永久に固まる。実際にこのバグを踏んだ
- タブ復帰時など、現在時刻が既にループ終端を過ぎている場合の追いつき処理を入れる（経過ループ数を計算して進める）
- 曲の切り替えを世代番号（generation）で管理し、古いtickを打ち切る

### タイマー間引きについて
非アクティブタブでは`setTimeout`が1秒間隔まで間引かれる。理論上、先読み200msでは音が途切れる。

ただし**実際にはノードの適切な解放（セクション1）を行った時点で、タブ裏での停止も解消した**。Web Workerタイマー化やSCHEDULE_AHEAD_SECの延長は、それでも問題が出る場合の手段として保留してよい。**症状が出ていないなら対策を入れるな。**

## 3. 信号経路の原則

### マスター段は最初からこう組む
```
各ノートのGain → masterGain → DynamicsCompressor → destination
                     ↓（送り）
                  Convolver（リバーブ）→ reverbWet → masterGain
```

コンプレッサーは**後付けではなく最初から入れる**。多パート同時発音は必ず飽和する。

推奨値と根拠：
```
threshold: -6   // 初版は -12。-12・ratio 6 では、ベースや和音が鳴るたびに全体が押し下げられ、音が詰まって揺れた
knee: 12        // 初版 18
ratio: 3        // 初版 6。ピークは抑えつつ、強弱の表現を潰さない
attack: 0.01    // 初版 0.003。速すぎると音の頭（アタック）まで潰す
release: 0.25   // 短すぎるとポンピング（音量の脈動）が出る下限
```
初版の値（-12・6・0.003）は「4〜6パート同時発音で合算ピークが-6dBFSを超えて歪んだ」ために入れた。ただ、音源を整理して（§6）ピークに余裕ができたら、上の弱い値の方が素直に鳴った。**「音が平板」「詰まる」「揺れる」と感じたら、ここを弱める。**

**DynamicsCompressorNodeは、threshold と ratio から自動で音量を持ち上げる（メイクアップ）。** 抑えを弱めると持ち上げも減り、全体が小さくなる（上の変更で約1.2dB）。後段に Gain（上の値なら 1.15）を挟んで戻すこと。戻さないと、聞き比べで「前の方が良い」と誤判定する（§7）。
```
masterGain → compressor → makeup(Gain 1.15) → destination
```

### リバーブの作り方
- **リバーブに低音を送らない。** 送り（共有Gain）と Convolver の間に highpass（**300Hz**、Q 0.7）を1つ挟む。低音の残響は溜まって「ボワーン」とこもる。ミックスの定番の手当てで、資料によって目安は 300〜600Hz。
- **合成インパルスレスポンスは、白色雑音を小さくしていくだけにしない。** 最後まで高域がシャーと残り、ざらついた響きになる。次の3つで部屋らしくなる：
  - 時間とともに閉じていく低域通過に通す（例：9kHz → 約0.7kHz。高い音ほど早く消える）
  - 頭に約20msの間（プリディレイ）を置く
  - 左右のチャンネルに別の雑音を使う（広がり）
- 作り直したら、**響きの総量（二乗和）を元のインパルスと揃える。** 揃えないと、質ではなく量の違いを聞き比べることになる。

### ノードの共有可否
| 対象 | 共有 | 理由 |
|---|---|---|
| リバーブ送りGain | **可** | convolverへ流すだけで原音経路に戻らない |
| BiquadFilter | **不可** | 下記参照 |
| Oscillator / 包絡線用Gain | 不可 | ノートごとに固有 |

**BiquadFilterを共有してはいけない理由：**

BiquadFilterは接続された全入力を合算してから処理する。ノートごとの経路が
```
osc → filter → gain(包絡線) → masterGain
```
の場合、filterを共有すると：
```
osc1 ┐
osc2 ├→ [共有filter] ┬→ gain1(包絡線1) → masterGain
osc3 ┘               ├→ gain2(包絡線2) → masterGain
                     └→ gain3(包絡線3) → masterGain
```
となり、**各gainに全ノートの合成音が流れ込む**。声部数が増えるほど二乗で膨れる。実際に唸り声のような音になって完全に破綻した。

フィルタが包絡線Gainより**後段**なら実害は出ないが、削減効果は小さい。**素直にノートごとに生成せよ。**

## 4. 曲の切り替え

音を`stop(now)`で即座に切ると、波形の途中で断ち切られてクリックノイズになる。持続音（padなど）が鳴っている最中ほど顕著。

**最初からこう作る：**
- 停止前にmasterGainを**40ms**かけて0へフェードし、その後にノードを停止
  - 根拠：20ms未満ではクリックが残り、100msを超えると切り替えが鈍く感じる
- 切り替え時に間を設け、開始時もフェードインする
  - 自動切り替え（曲送り）：**0.8秒** — 前曲の残響が減衰しきる長さ。リバーブが短ければ0.5秒程度でよい
  - 手動切り替え：**0.12秒** — 操作への反応として「即時」と感じられる上限

曲間の間は技術的な必要だけでなく、音楽的な区切りとしても機能する。

### 全曲連続再生の順番表
曲順を ID の配列で持つ場合、**曲を足したときに配列へ書き忘れると、その曲は黙って飛ばされる**（実際に起きた）。順番表に無い曲は、表の曲のあとに曲一覧の順で続ける作りにしておく。
```js
const order = FIXED_ORDER_IDS.map(id => TRACKS.findIndex(t=>t.id===id)).filter(i=>i>=0);
TRACKS.forEach((t, i)=>{ if(!order.includes(i)) order.push(i); });
```

## 5. 曲データの持ち方

```js
{
  id: '一意な文字列',
  title: '曲名',
  bpm: 数値,
  loopSec: ループ長（秒）,
  instruments: { melody: '音色名' },  // 省略時は既定音色
  melody: [[開始秒, MIDIノート番号, 長さ秒, ベロシティ], ...],
  arp: [...], pad: [...], bass: [...]
}
```

### loopSecの使い方
**実際の音の長さより長く設定すると、差分が自動的に静寂になる。** 末尾に余韻や間を作りたいときは、無音データを書くのではなくloopSecを伸ばす。「一度鳴って、間を置いて再演」もこれで実現できる。

### 音色は差し替え可能にする
音色関数を`(startTime, midi, dur, vel)`の統一シグネチャで実装し、辞書で引く形にしておく。曲データ側で`instruments`を指定すれば、同じ譜面のまま音色だけ差し替えられる。**音色の比較検討が劇的に楽になる。**

## 6. 音色設計の勘所

- **減衰音（musicbox, bell系）ばかりで固めるとピコピコした電子音になる。** 持続音（笛、ストリングス、pad）を混ぜて「面」を作ること
- **高域の鋭いアタックは耳に刺さる。** ローパスをかけるか、音色自体を持続音に変える
- **リバーブがないと全ての音が「近く」聴こえ、感動的な場面が作れない。** ConvolverNodeに合成インパルスレスポンス（2〜3秒程度）を持たせるだけで大きく変わる
- ベロシティを固定値で並べると機械的になる。フレーズ頭を強く、句尾を弱く

### 包絡線（エンベロープ）の落とし穴
- **`exponentialRampToValueAtTime` で 0.0001 から立ち上げると、聞こえ始めが遅れる。** 指数カーブは時間のほとんどをほぼ無音で過ごし、最後に一気に上がる。最大から -10dB に届くまでの時間は、0.9秒の立ち上がりで約0.8秒、0.15秒でも約0.13秒。パッドが拍より遅れて聞こえた原因はこれだった。
  - 指数の立ち上がりは、10ms 以下の短いアタック（打鍵・撥弦）だけに使う。
  - 柔らかく立ち上げたい持続音は、`setValueAtTime(0)` → `linearRampToValueAtTime(peak, t + 0.03)` のように直線で入る。柔らかさは音色（倍音を減らす）で出す。
- 持続音を最後まで同じ大きさで伸ばすと、平たく電子的になる。伸ばしている間に少しずつ弱める（例：`setTargetAtTime(peak*0.7, t, 時定数)`）と、弦や声のように聞こえる。

### 低音を濁らせない
- ベースは1音の伸びを短くして、次の音と重ねない（例：release 最長 1.1秒 → 0.5秒）。低音が重なると溜まって「ボワーン」となる。
- ベース以外の持続音（パッドなど）は、150Hz より下を highpass で切る。低音はベースに任せる。
- リバーブに低音を送らない（§3）。
- 音量で測ると、低域は全体より十数dB 小さくても「ボワーン」と感じる。原因は量ではなく、膨らむ鳴り方と残る長さのことが多い。

### 音色ごとの知見
- **打楽器・撥弦の上の音は整数倍ではない。** 片端を固定した板（オルゴールの櫛歯・カリンバ）の2番目の振動は、基音の約6.27倍（梁の理論）。こうした音は、弾いた瞬間だけ鳴ってすぐ消える（カリンバの測定）。
- オルゴールの実測（英国オルゴール協会の会誌、要約のみ確認）では、耳に届く音に 2倍（基音から -24dB）・3倍（-16dB）が乗る。正弦波2本（基音＋2倍を -12dB）の素朴な作りは、2倍が強すぎてこもる。
- 弾いた瞬間の雑音（数ms の雑音を高めの帯域に通す）を足すと、合成音らしさが減る。雑音のバッファは1つ作って使い回す。
- **高い音は耳に刺さる。** 耳は2〜5kHz に敏感なので、1.4kHz 付近より上は周波数に反比例して弱める（倍音はさらに強く）。
- **三角波は低い所でブーと濁る**（奇数倍音）。伴奏には、正弦波に2倍音を少し（0.12程度）足した音の方が柔らかい。
- **パッドは、音の高さを数セントずらした声を重ね、左右に置く**（例：±6セントで左・中・右）。正弦波だけの1点からの音より、揺らぎと広がりが出る。1声の波形は `createPeriodicWave` で正弦波に2倍・3倍を少し足すと、発振器を増やさずに済む。
- `PeriodicWave` や雑音のバッファは AudioContext ごとに作る（オフライン書き出しの OfflineAudioContext で、実時間用のものは使えない）。

## 7. 開発の進め方

- **1回の修正で1項目だけ変える。** 複数同時に入れると、破綻したとき原因が特定できない
- **修正のたびにファイル名を分ける（v1, v2...）。** 上書きするとロールバックできない
- **「理論上安全」を実機確認なしに信用しない。** 本書のフィルタ共有の項は、理屈としては筋が通って見えたが実際には破綻した実例である
- **AIに実装させる場合も、AIの診断を検証してから着手させる。** 症状の説明として一見もっともらしくても、実際の原因が別の行にあることがある
- **症状は時刻・数値・状態をセットで記録する。** 「何分後に何MBで何が起きたか」の記録が、原因特定の決定打になる
- **症状が消えたら手を止める。** 予防的な追加実装は、次に何か起きたときの切り分けを濁らせる

### 音色の聞き比べ
- 音の良し悪しは、数値ではなく人の耳が決める。**新旧を切り替えられる形で入れる**（例：URL 引数 `?mix=1` で前の音に戻す）。採用が決まるまで、既定は前の音のままにする。
- 音の経路を作る関数に AudioContext を引数で渡せる形にしておくと、**OfflineAudioContext で同じ曲を同じ時間軸のまま書き出せる。** 曲の頭30秒を新旧で書き出して渡すと、実機で聞き比べてもらえる。
- **聞き比べる前に、新旧の音量（平均と最大）を ±0.5dB 以内に揃える。** 大きい方が良く聞こえてしまう。ffmpeg の `volumedetect` で測れる。帯域ごと（`lowpass`・`highpass` を前に挟む）に測ると、どこが変わったかも分かる。
- 他のパートに埋もれる変更（パッドなど）は、**そのパートだけを書き出す**と違いが分かりやすい。
- 複数の改良は一度に入れず、**一つずつ足した版を順に書き出す**。どれが効いたかを耳で分けられる。

## 8. 実装後の確認項目

- [ ] 数時間の連続再生で音が劣化しないか
- [ ] **メモリ使用量の下限値（GC後の谷）が上がり続けていないか** ← 最重要
- [ ] **低スペック環境で数分間持つか。** 高スペック機では設計の欠陥が余力で隠れる
- [ ] タブを裏に回して30分放置後、復帰時に音が重なっていないか
- [ ] 曲の切り替えでノイズが出ないか
- [ ] 全曲連続再生モードがある場合、1周させて無音化しないか
- [ ] **全曲連続再生で、全部の曲が順に流れるか**（順番表に書き忘れた曲が飛ばされていないか。§4）
- [ ] ゆっくり立ち上がる持続音が、拍より遅れて聞こえないか（§6）
- [ ] 音色や経路を変えたあと、全体の音量が前と揃っているか（§3・§7）
- [ ] 効果音を連続で鳴らしても蓄積しないか
- [ ] **モバイル実機（特にiOS Safari）で確認したか** — デスクトップと挙動が異なる。無音になる、AudioContextが勝手にsuspendする、同時発音数の上限が低い等。**シミュレータではなく実機で確認すること**
